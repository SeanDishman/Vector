# Stack-discovery tools and practical improvements for Vector

Researched 2026-11-09 UTC using public product documentation, public source documentation and the current Vector workspace. This is a research result, not a claim that the proposed features or API integrations have shipped. No target was submitted to an external scanner and no public-host Vector test was run.

Implementation update: the DNS recommendation below is now implemented in `src/dns.cpp`, with automatic collection, role matching and native evidence display. See [DNS infrastructure](dns-infrastructure.md) for its actual scope and verification. Other rows remain research recommendations.

The most useful references are Wappalyzer for general technology fingerprints, BuiltWith for dated observations, urlscan for browser evidence, and Shodan/Censys for host services. PublicWWW and NerdyData can help investigate unfamiliar code signatures. These sources cover different kinds of evidence; their combined count is not a count of software proven to run on one IP.

## Comparable services

| Tool | What its public documentation establishes | How Vector can use it |
| --- | --- | --- |
| [Wappalyzer](https://www.wappalyzer.com/technologies/) | Identifies technologies from public HTML, scripts, headers and cookies. Its [lookup API](https://www.wappalyzer.com/docs/api/v2/lookup/) offers cached or live results and deeper multi-page crawls. Deep live lookup is asynchronous; the documentation allows up to 15 minutes. | Expand the evidence channels and reusable technology rules in the local engine. An optional API adapter could provide a separately dated external result. The commercial lookup API currently requires a Business plan. |
| [BuiltWith](https://api.builtwith.com/) | Offers current/historical technology records and change information. Its [Domain API](https://api.builtwith.com/domain-api) includes live-only and date filters; a [dedicated live API](https://api.builtwith.com/dedicated-domain-live-api) is also documented. | Preserve observation time and changes across inspections. If an API is added, use its documented key-based interface and retain its source/date; do not make historical detections look like today's local responses. |
| [urlscan](https://docs.urlscan.io/) | A browser records contacted domains/IPs, requested resources, page content, screenshots and a DOM snapshot. Existing scans can be searched and retrieved. | Use it as a model for explaining and replaying browser evidence. Optional retrieval of existing results can help diagnose differences in location/time. Result, DOM and response-body retrieval require authentication under its [May 2026 change](https://urlscan.io/blog/2026/03/18/api-auth-required/). |
| [WhatWeb](https://github.com/urbanadventurer/WhatWeb) | Public source documents per-product plugins, URL/tag/regex/hash matches, and follow-up probes triggered by an initial detection. | Give Vector each rule a clear identity, matching evidence and positive/negative fixtures. Consider only narrowly justified follow-up reads inside existing bounds. Vector's project rules prohibit importing its plugin corpus. |
| [Shodan](https://developer.shodan.io/api) | Its host lookup API returns services previously found at an IP, with optional historical banners. | Optional read-only host enrichment when a service is silent locally, or as a comparison against an observed banner. Keep these external observations distinct from current reachability and the current device's identity. |
| [Censys](https://docs.censys.com/docs/platform-host-dataset) | Host records preserve protocol, port, banner, software, certificate, favicon and scan-time information. [Web properties](https://docs.censys.com/docs/censys-platform-faq) distinguish hostname-based HTTP observations from IP-host records. | Improve evidence scope: associate a result with the hostname, URL, port and response that justified it. Optional API results need the same provenance. Shared IPs, certificates and icons do not establish a single machine or company. |
| [PublicWWW](https://publicwww.com/) | Searches HTML, JavaScript, CSS and HTTP-header content; exposes snippets and an API. | Investigate an unfamiliar, non-sensitive asset/marker and locate candidate examples for signature research. Search hits must be checked against actual product evidence before adding a general rule. |
| [NerdyData](https://www.nerdydata.com/) | Source-code/technology search and domain lookups; [API access](https://www.nerdydata.com/api) requires an account. | Another research source for unfamiliar markers and an optional technology-data provider. Do not copy its company inventories into Vector. |
| [WhatRuns](https://whatruns.com/how-it-works) | A browser extension shows technology identifications for the visited page. Its [product page](https://help.whatruns.com/) also describes change notifications. | Useful for a manual comparison on authorized pages. The inspected pages do not establish a public integration API or expose the full matching engine. |

The public [Ahrefs Wappalyzer fork specification](https://raw.githubusercontent.com/ahrefs/Wappalyzer/master/README.md) is particularly useful architectural documentation: it describes DOM selectors/properties, runtime variables, DNS records, cookies, CSS, scripts, request URLs and rule prerequisites/exclusions. It is a public fork; its schema is not proof of the current commercial service's implementation. These are methods to learn from, not permission to import third-party rules or a ready-made database of companies.

## What Vector already has

The current source contains isolated Chromium execution, dynamic script collection, runtime checks for several libraries, rendered-DOM inspection and retained network initiators in [browser.cpp](../src/browser.cpp). It also has generic linked-document discovery and bounded structured disclosure extraction in [disclosures.cpp](../src/disclosures.cpp) and [disclosure_rows.hpp](../src/disclosure_rows.hpp). Company-specific provider catalogs have been removed.

[fingerprint.cpp](../src/fingerprint.cpp) already records cookie names, header order, favicon hashes and TLS-related fingerprints. The ordinary rules in [detector.cpp](../src/detector.cpp) match headers, asset URLs, selected markup and JavaScript evidence. The practical gap is broader, better-qualified matching and document coverage, not simply adding another browser or hashing the same icon again. This is a source inspection; it does not certify every concurrent build/package.

## Recommended implementation order

These priorities are engineering recommendations derived from the sources and local evidence above. They are not claims made by those services about Vector.

| Priority | Concrete change | Existing extension point | Evidence that would demonstrate improvement |
| --- | --- | --- | --- |
| 1 | Support provider heading sections followed by address/service paragraphs; then bounded PDF text extraction and structured public disclosure responses. Preserve document position or JSON pointer and the discovery chain. | `src/disclosure_rows.hpp`, `src/disclosures.cpp`, disclosure-purpose browser collection | The saved Default document currently yields 0/22 names; extract its 22 sections without a domain rule, then pass generated-name variants and customer/history/hidden negatives. Supabase's saved page links PDFs, so a separate PDF fixture is needed. |
| 2 | Expand general fingerprint rules across runtime APIs, DOM properties, stylesheet content and cookie names. Use explicit all/any conditions, prerequisites and conflicting evidence; retain a rule ID and matched value. | `src/detector.cpp`, `src/browser.cpp`, `src/fingerprint.cpp` | Identify real production bundles with hashed filenames and no global library variable; reject documentation strings, fake globals, generic cookies and shared styles. Do not infer an unadvertised version. |
| 3 | Add bounded DNS evidence for CNAME, MX, NS and relevant TXT records. Label mail, DNS and hosting roles separately. | New small DNS collector beside `src/scanner.cpp`; report model | Local DNS fixtures identify an unfamiliar mail/hosting arrangement, retain TTL/source, and never turn an MX provider into the website's backend or a domain-verification TXT record into current product use. This is a new capability, not currently established by address resolution. |
| 4 | Add a compact evidence snapshot and comparison format: resource URL/type/status, initiator, body hash, truncation, rule ID, origin and observation time. | `src/include/vector/model.hpp`, `src/browser.cpp`, `src/report.cpp` | Replay retained responses without network access; distinguish a collection failure from an absent signature. Compare old/new captures without treating an absent observation after a blocked scan as a removal. Existing browser request records should be extended, not duplicated. |
| 5 | Add optional external lookup adapters, starting with Wappalyzer or BuiltWith for websites and Shodan/Censys for IPs. urlscan is most useful for retrieval and diagnostic evidence. | Separate enrichment component, not `identify_http` | Mock responses prove that stale/conflicting records keep their provider, subject and dates and cannot override a current local response. Authentication, quotas and failures remain explicit; no account is required for normal Vector inspection. |

General product fingerprints are different from company answer lists. A rule that checks a library's documented runtime API works on any site exposing that API. A stored assertion that a named company uses a particular provider is the approach the user rejected. Published provider names must continue to come from the collected source document.

## How to evaluate these methods

Keep four measurable outputs: current observed website technologies, contacted integrations, published company providers and externally reported/historical records. Compare precision and recall within each output against the same captured page/document and observation time. Record collection failures and bytes analyzed alongside detections. A combined badge count hides the cause of a miss.

The existing [fresh-name discovery checks](provider-discovery-verification.md) establish that opaque links and legal/privacy chains can lead to names absent from the executable. They do not establish coverage of PDFs or every document layout. The saved Default failure is an immediate regression target, rather than another list to bake into the program. Browser and fingerprint comparisons should similarly use local replays or authorized fixtures, with one deliberately misleading negative for every new rule.

Vector's automatic 12-page, 40-static-script and 30-second web limits should remain intact. Spend the budget on evidence suggested by the page and analyze already collected responses more effectively. Deeper historical datasets from external services can complement this bounded scan, but need their own source and date. None of the inspected public documentation establishes a way to identify private backend components from a public page with certainty.

## Research outcome and limits

The recommended next work is stronger local matching and broader document extraction, followed by DNS-role evidence. Optional external APIs are useful for coverage and comparison; they are not required to fix the known Default-format failure. No API integration, signature corpus import, external account setup or production code change was made during this research. The report documents feasible approaches and verification targets, not measured superiority over StackFull or any other service.
